#### FO3-2026-10-12-D2-01: Quest-level dialogue conditions (`QustRecord.dialogue_conditions`) are parsed and never evaluated; with quest-priority ordering, the identity-less INFOs of high-priority quests answer every other speaker's greeting
- **Severity**: HIGH. This is the opening line of essentially every FO3 / FNV conversation (the generic `GREETING` topic is the only activation path for a quest-less FO3/FNV NPC), and it is wrong for the large majority of speakers. No crash or data loss, but the defect fires under the most ordinary condition in the dialogue layer, with no workaround short of the fix.
- **Dimension**: 2 — ESM data slice → dialogue selection. The mechanism owners are `/audit-scripting` (condition evaluation, `select_info`) and `/audit-gameplay` (`npc_dialogue.rs`). Labels: `game:fo3`, `game:fnv`, `legacy-compat`, `dialogue`, `quests`, `scripting`, `high`, `bug`.
- **Location**:
  - `crates/plugin/src/esm/records/misc/quest.rs:363` and `:1139` — `dialogue_conditions` is filled and has **no consumer** (`grep -rn dialogue_conditions crates byroredux/src` finds only the field, the push and one parse test).
  - `crates/scripting/src/dialogue.rs:309-366` (`select_info`) — orders by `DialogueQuestPriorities`, then evaluates only `info.conditions`.
  - `byroredux/src/systems/npc_dialogue.rs:322-336` (`open_conversation` → `generic_greeting_record` → `select_on_topic`).
  - `byroredux/src/asset_provider/script.rs:631` — the priorities are installed unconditionally; no quest-condition resource exists.
- **Status**: NEW. Searched: "quest dialogue conditions", "QUST CTDA dialogue", "quest-level", "WaterBeggars", `dialogue_conditions` (open and closed, `docs/`). Related but not covering: #5271 (closed — fixed only the per-INFO `QSTI` running-state half; `AUDIT_GAMEPLAY_2026-10-05.md:144` left "have `/audit-scripting` decide on applying quest-level dialogue conditions", never filed); ESM-2026-10-09-D4-01 (the Pitt flip is one symptom).
- **Description**:
  - The GECK defines the rule: *"Quest Conditions: Any conditions here are considered to apply to all dialogue in the quest. The quest conditions are checked first; only if those are true are the conditions on the infos evaluated"* (`geck-uesp-wiki/(main)/Quest Data Tab.wiki:9`).
  - FO3/FNV author the speaker identity of whole quests there, not on the INFOs:
    - `WaterBeggars` (priority 75, Start Game Enabled, no script): quest condition `GetInFaction` (fn 71). Its `GREETING` INFOs: 3 with **no CTDA at all** (Random, one Random End), 5 with only `GetActorValue` (fn 14), 1 with only `GetDistance` (fn 50).
    - `DLC01DialogDowntown` (Pitt, priority 50): 13 OR'd fn 427 (`GetIsVoiceType`, VTYP parameters) quest conditions; its "Go away." has no INFO CTDA.
    - `FFHitSquadQuest` (50): `GetInFaction`, 4 unconditioned INFOs. `Doctors` (75): 3 quest conditions, 3 INFOs with only fn 14.
    - 31 of the 100 `Fallout3.esm` quests that own `GREETING` INFOs carry quest-level conditions (894 of the 2,542 master INFOs sit under them).
  - `select_info` sorts every INFO of the topic by quest priority (descending, file order in a tie) and takes the first that passes its own conditions. With the quest list unevaluated, an unconditioned INFO of a priority-75 quest passes for everyone and out-ranks every priority-≤60 speaker-specific greeting (the main-quest, companion and town quests are 50–61).
- **Evidence** (the engine's own code over the shipped data; `/tmp/audit/fo3/greetprobe`: parse `Fallout3.esm`, start every Start-Game-Enabled quest as `quest_startup_system` does (141), install `DialogueQuestPriorities`, then `select_first_info(GREETING, world, npc, player)` with the speaker's `SceneAliasCandidate.base_form_id` set to the NPC base):
  ```
  quests started=141  GREETING form=000000C8 infos=2542
          <bare>: INFO 000C6E7E quest=WaterBeggars prio=75 "Please... do you have any water? I'm so thirsty..."
      MoiraBrown: INFO 000C6E7D quest=WaterBeggars prio=75 "Can you help me? I need water... purified water... please..."
        ThreeDog: INFO 000C6E7F quest=WaterBeggars prio=75 "Please! Please help me... I need water! I'm dying!"
MegatonSettler01: INFO 000C6E7D quest=WaterBeggars prio=75 ...
           Amata: INFO 000C6E7C quest=WaterBeggars prio=75 "Oh, thank God. Someone new! I need water! Please! Water!"
  all 1647 NPC_ bases (non-creature): 1647 x WaterBeggars
  ```
  Same probe on `FalloutNV.esm`: 3,788 of 3,816 `NPC_` bases select `vDialogueEDE` (priority 75; its INFO `0x001579D7` "{Curious Beep}<Makes beeping sounds>" has **zero INFO CTDAs**, the ED-E identity lives in 3 OR'd `GetIsID` quest conditions). The 28 exceptions are the speakers whose own quest outranks it (`VCG01` is 76, so Doc Mitchell works, which is why `dt1-dialogue-layers.sh` passes). Caveat: the probe uses bare speakers (no factions / actor values), so a speaker whose own INFO wins at priority ≥ 75 is found, and any INFO that would pass for a real speaker only widens the set; the unconditioned INFOs pass regardless of components. No live engine run was possible (user's session is live).
- **Impact**:
  - Activating nearly any FO3 NPC without a >75-priority greeting speaks a water-begging line. On FNV the same defect gives ED-E beeps. (With `ThePitt.esm` loaded, the Pitt's unconditioned "Go away." is out-ranked by `WaterBeggars` today; it would surface for every speaker below priority 50 as soon as `WaterBeggars` is gated, so the Pitt's 13-voice-type quest list must be honoured in the same change.)
  - The voice resolver composes the name from the selected INFO's quest, so a non-matching voice type resolves nothing and the line falls back to the subtitle estimate.
  - Conversation-state side effects of the wrong INFO (`OnBegin` fragments, the Goodbye close, `note_info_spoken` keyed on the wrong line) run for the wrong line.
  - The existing guards cannot see it: `dt1-dialogue-layers.sh` gates Doc Mitchell (priority 76, above the hijackers); the FO3 floor test (`dialogue_greeting_and_forcegreet_fo3_floor`) counts INFOs and PACKs, not the winner; `fo3` dt1 is a declared SKIP.
- **Related**: #5271 (closed; its quest-priority ordering is what turns the missing gate into a pre-emption), ESM-2026-10-09-D4-01 / #5494 (the Pitt "Go away." flip, a symptom), FNV-2026-10-12-D2-01, #5426, #5397, `AUDIT_GAMEPLAY_2026-10-05.md` GAME-D2-2026-10-05-01 (deferred half). FNV reach: the FNV leg did not report this; route it to the same fix.
- **Suggested Fix**:
  - Install `QustRecord.dialogue_conditions` beside `DialogueQuestPriorities` (a `DialogueQuestConditions` resource, quest → `ConditionList`; Skyrim's `dialogue_conditions` ride the same field) and evaluate it in `select_info` before each INFO's own list, with the same subject / target / quest `ConditionContext`; memoise per quest within one call.
  - **Coupled prerequisite**: an uncatalogued function evaluates to `0.0` (`evaluate_function`, `ConditionFunction::Unknown`), so `fn == 1` fails closed. The `Fallout3.esm` quest-level lists use `GetIsVoiceType` (fn 427, 10 quests / 71 conditions — the `GenericAdult` / `GenericRaider` / Pitt gates, VTYP parameters) and fn 372 (11 quests), neither in the catalog. Gating before cataloguing them would drop the generic fallback quests entirely, so catalogue 427 (the speaker's `VTCK`) and 372 first, or decline a quest list that contains an uncatalogued function (the #5380 "unknown-fn decline" shape).
  - Pin it with two real-data tests (FO3: the bare-speaker `GREETING` must not resolve to `WaterBeggars`; FNV: not to `vDialogueEDE`) next to `dialogue_greeting_and_forcegreet_*_floor`, plus a synthetic priority-vs-quest-gate case in `dialogue.rs`. Add a named-speaker assertion to the FO3 dt1 so the SKIP can be lifted.
